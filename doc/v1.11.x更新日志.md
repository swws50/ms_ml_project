## v1.11.1 (2026-03-08)

### 修复 UI 启动时逐步渲染的视觉问题

#### 问题现象

应用启动时，主界面不是一次性完整出现，而是按照代码执行顺序逐步显示：先出现根窗口和菜单栏，然后是三个主面板（预处理 / 控制 / 结果 / 预测），最后才出现顶部状态栏 chip 行。整个过程持续约数百毫秒，用户能明显感知到界面"从上往下一块一块拼出来"的动画感。

#### 根本原因分析

**原因一：组件创建顺序不符合视觉层次**

`_create_layout` 中的调用顺序为：

```
_create_menu_bar()        # row=0  菜单栏
_create_ui_panels()       # row=3,5,6  三个主面板（耗时最重）
_create_global_progress() # row=1,2,4  状态栏 chip + 分割线
```

tkinter 的 grid 几何管理器在每次 `.grid()` 调用后都可能触发一次局部重绘。由于主面板（`PreprocessingPanel`、`ControlPanel`、`ResultPanel`、`PredictionPanel`、`VisualizationPanel`）包含大量子组件，创建时间远长于轻量的 chip 行，因此用户先看到面板、后看到状态栏。

**原因二：`root.update()` 在初始化期间被反复调用**

`utils.py` 的 `log_message` 函数每次写入日志后都调用 `root.update()`，目的是让日志文本框实时滚动到最新一行。但 `root.update()` 会强制 tkinter **立即处理所有挂起的事件和重绘请求**，相当于在初始化中途强插了一次"把当前已创建的组件全部渲染到屏幕上"的操作。

此前曾尝试 `root.withdraw()` + `root.deiconify()` 来隐藏初始化过程，但失败了——原因正是 `root.update()` 的介入：`withdraw` 的本质是把窗口从操作系统的屏幕上 **unmap（解除映射）**，但 `update()` 被调用时 tkinter 会重新处理窗口映射状态，导致 `withdraw` 的效果被提前撤销，部分渲染内容透漏给了用户。

#### 修复方案

**修复一：调整创建顺序（`main.py`）**

将 `_create_global_progress()` 移到 `_create_ui_panels()` 之前，使状态栏 chip 在主面板之前创建，至少保证视觉层次从上到下是正确的：

```python
# 修复前
self._create_menu_bar()
self._create_ui_panels()
self._create_global_progress()

# 修复后
self._create_menu_bar()
self._create_global_progress()   # 状态栏先于主面板创建
self._create_ui_panels()
```

**修复二：用窗口透明度代替 withdraw/deiconify（`main.py`）**

在 `_setup_window` 末尾，几何尺寸设定完成后，立即将窗口透明度设为 0：

```python
self.root.attributes('-alpha', 0)
```

在 `_finalize_setup` 末尾，所有组件创建完毕后，通过 `after(0, ...)` 恢复透明度：

```python
self.root.after(0, lambda: self.root.attributes('-alpha', 1))
```

#### 背景概念：`-alpha` vs `withdraw`

|                | `withdraw`    | `-alpha=0`               |
| -------------- | ------------- | ------------------------ |
| 本质             | 将窗口从屏幕 unmap  | 将窗口渲染为完全透明               |
| 窗口是否"存在"       | 否（已解除映射）      | 是（仍在屏幕上，只是不可见）           |
| `update()` 的影响 | 可能重新 map，破坏遮挡 | 无影响，透明属性不受 `update()` 干扰 |
| 用户能看到中间状态      | 有风险           | 不会                       |

`-alpha=0` 让窗口以"隐形"状态完成所有渲染，无论中途触发多少次 `update()`，用户都看不到任何中间状态。

#### 背景概念：`root.after(0, callback)` 是什么

tkinter 是单线程的，所有 UI 操作都在一个线程里按顺序执行。`mainloop()` 是这个线程的"主循环"，它不断地从一个事件队列里取出事件（鼠标点击、键盘输入、定时器到期、重绘请求……）并依次处理。

`root.after(delay_ms, callback)` 的作用是：**把 callback 作为一个定时事件注册进队列，在 delay_ms 毫秒后被 mainloop 取出并执行。**

`after(0, callback)` 的特殊之处：delay 为 0 并不意味着"立刻执行"，而是"尽快执行"——具体来说，是等 mainloop **本轮正在执行的所有同步代码都跑完之后**，在下一次 dispatch 事件时才执行。

在本次修复中，这个时序至关重要：

```
__init__ 开始
  _setup_window()  → root.attributes('-alpha', 0)              # 窗口变透明
  _init_managers()
  _create_layout()                                              # 创建所有组件（透明状态下渲染，用户看不到）
  _finalize_setup()
    log_message(...)  → root.update()                          # 强制刷新，但窗口仍透明，用户看不到
    root.after(0, lambda: root.attributes('-alpha', 1))        # 注册"恢复可见"事件到队列
__init__ 结束
mainloop() 启动
  → 取出 after(0,...) 注册的事件 → root.attributes('-alpha', 1) # 界面一次性完整显示
```

如果不用 `after` 而是直接在 `_finalize_setup` 末尾调用 `root.attributes('-alpha', 1)`，效果理论上相同。但 `after(0, ...)` 更保险——它确保了恢复可见一定发生在 `mainloop()` 正式接管控制权之后，而不是在 `__init__` 还未结束、事件队列仍可能有残留重绘请求的时候。

## v1.11.2(2026-03-08)

### 新增启动闪屏（Splash Screen）

#### 背景

v1.11 引入了 `-alpha=0` 方案使主界面在初始化完成前完全透明，消除了逐步渲染的视觉问题。但这同时带来了一个新问题：初始化期间屏幕上什么都没有，用户不知道程序是否在运行，体验有"假死"感。

#### 方案探索过程

**尝试一：镂空透明图标窗口**

最初使用 `tk.Toplevel` + `overrideredirect(True)` + `-transparentcolor` 尝试显示透明背景的图标。`-transparentcolor` 的原理是把窗口上指定颜色的像素穿透显示底层内容（桌面），实现镂空效果。

但遇到两个问题：

1. **白边（抗锯齿边缘问题）**：PNG 图标边缘存在半透明像素（抗锯齿），tkinter 不支持逐像素 alpha，这些像素会被二值化处理（低于阈值变全透明显示白色，高于阈值变全不透明），造成锯齿白边。尝试用 PIL 的 `Image.alpha_composite` 预先将半透明像素合成到背景色上再传给 tkinter，可减轻但无法彻底消除——因为边缘混合色不等于背景色，`-transparentcolor` 无法穿透。
2. **`-transparentcolor` 的根本局限**：只能对完全匹配的单一颜色做穿透，无法做逐像素 alpha，是"抠色"而非真透明。

**结论**：tkinter 原生不支持逐像素 alpha 窗口（需要调用 Windows `UpdateLayeredWindow` API，约 50 行 ctypes 代码，且平台限定）。

#### 最终方案：卡片式闪屏

放弃透明，改为白色背景的卡片窗口，干净清晰，无任何边缘问题：

```
┌─────────────────────┐
│                     │
│       [图标]         │
│      DETEQX         │
│      正在启动...     │
│                     │
└─────────────────────┘
```

#### `main.py` 变更

新增 `_create_splash()` 方法：

- 创建无边框 `Toplevel`（`overrideredirect=True`），白色背景，置顶
- 用 PIL 将图标缩放至 128×128，alpha_composite 合成到白底后传给 tkinter（避免白边）
- 图标下方显示应用名 `DETEQX`（Segoe UI 18px Bold）和副标题 `正在启动...`（9px 灰色）
- 使用 `tk::PlaceWindow {splash} center` 居中（相比手动计算 `winfo_screenwidth()`，能正确处理 Windows DPI 缩放导致的偏移）

`_setup_window()` 中在设置 `-alpha=0` 之后立即调用 `_create_splash()`，闪屏先于主界面出现。

`_finalize_setup()` 中将原来的单行 `after(0, ...)` 扩展为具名函数 `_on_init_complete()`，在恢复主窗口透明度的同时销毁闪屏，两者同步切换：

```python
def _on_init_complete():
    self.root.attributes('-alpha', 1)
    if self.splash:
        self.splash.destroy()
        self.splash = None
self.root.after(0, _on_init_complete)
```

## v1.11.3 (2026-03-08)

### 修复子窗口在高 DPI 屏幕下无法居中的问题

#### 问题现象

在 Windows 高 DPI 缩放（如 150%）环境下，所有子窗口（闪屏、对话框等）出现在屏幕左上角区域，而非预期的屏幕正中。

#### 根本原因

CustomTkinter 会主动声明进程为 DPI 感知（DPI-aware），此后 Windows 窗口管理器用**物理像素**定位窗口。但 tkinter 的 `winfo_screenwidth()` / `winfo_screenheight()` 返回的是**逻辑像素**（物理像素 ÷ 缩放比），`winfo_fpixels('1i')` 也被 Windows 虚报为 96 DPI，导致两套坐标体系对不上：

- 逻辑屏幕（tkinter 认为）：1707 × 960
- 物理屏幕（实际）：2560 × 1440
- 计算出的"中心"：x=757, y=351（逻辑坐标，但被 OS 当物理坐标使用）
- 实际落点：屏幕左上角三分之一处

#### 修复方案

新增工具函数 `center_window(window, width, height)`（`utils.py`），使用 `ctypes.windll.user32.GetSystemMetrics(0/1)` 直接向 Windows 查询物理分辨率，绕过 tkinter 的逻辑像素报告：

```python
import ctypes
sw = ctypes.windll.user32.GetSystemMetrics(0)  # 物理宽
sh = ctypes.windll.user32.GetSystemMetrics(1)  # 物理高
scale = sw / window.winfo_screenwidth()         # 实际缩放比
x = (sw - int(width * scale)) // 2
y = (sh - int(height * scale)) // 2
window.geometry(f"+{x}+{y}")                   # 仅设置位置，不覆盖窗口大小
```

非 Windows 平台（Linux/macOS）`ctypes.windll` 不存在，自动 fallback 到原始 tkinter 方法（在这些平台上 DPI 处理机制不同，原方法即可正常工作）。

当前已将此函数应用于 `_create_splash()`，后续其他子窗口的居中逻辑将统一替换为此函数。

## v1.11.7 (2026-03-17)

### 修复预测报「无法检测训练特征」；重构模型加载与重置机制

#### 问题一：预测失败 — 「无法检测训练特征」

**现象**：在某些工作流下执行预测，结果面板显示「预测失败: 无法检测训练特征」。

**根本原因**：模型保存时只保存了 sklearn 对象，未附带训练特征的 m/z 列表：

```python
# 修复前
dump(self.best_model, model_path)
```

预测时 `load_training_features` 需读取训练 CSV 推导特征列表。若当前会话未通过「选择 CSV 文件」设置 `data_store._training_data_path`，且输出目录下的 `data.csv` 不存在，则返回 `None`，预测失败。此 bug 此前因用户总在同一会话内按顺序完成「预处理 → 选 CSV → 训练 → 预测」而未触发。

#### 问题二：加载不同模型时特征缓存不刷新

加载旧格式 `.joblib` 时，原 `_apply_loaded` 只赋值 `self.model`，不清空 `feature_detector.training_features`。若之前加载过 bundle A（特征已缓存），再加载模型 B，特征对齐会用 A 的 m/z 列表对 B 做预测，静默出错。

#### 问题三：重置后 `PredictionManager` 状态残留

`handle_reset_progress()` 调用 `data_store.clear_all_data()` 清空了数据存储，但 `PredictionManager` 实例本身的 `model`、`temp_model_path`、`feature_detector` 缓存未被清除。重置后若 `temp_model_path` 仍有值，下次预测会直接用旧文件路径，等于重置未生效。

---

#### 修复方案

**`model_training.py` — `save_training_results()`**

保存模型时将特征元数据一并打包为 bundle：

```python
model_bundle = {
    "model": self.best_model,
    "training_features": training_features,  # m/z 浮点列表，从 df.index 提取
    "normalization_method": norm_method,     # 'max'/'sum'/'median'/None
}
dump(model_bundle, model_path)
```

**`model_predictor.py` — `_apply_loaded()` 不再兼容旧格式**

旧格式 `.joblib`（直接是 sklearn 对象）不再被支持，遇到非 bundle 直接报错而非静默使用错误特征：

```python
def _apply_loaded(self, loaded, source_label):
    if not (isinstance(loaded, dict) and "model" in loaded):
        raise ValueError("模型格式不兼容，请使用当前版本重新训练以生成 bundle 文件")
    self.model = loaded["model"]
    features = loaded.get("training_features") or []
    self.feature_detector.training_features = features if features else None
    self.feature_detector.normalization_method = loaded.get("normalization_method")
```

每次加载都完整覆写 `feature_detector`，不存在缓存残留问题。

**`model_predictor.py` — `load_model()` 简化为 3 条路径**

移除原「内存中持有纯 sklearn 对象」的路径 2（该路径绕过 `_apply_loaded`，在多模型切换场景下会用错特征）。现在所有路径都经过 `_apply_loaded`，始终从 bundle 文件读取特征：

```
路径 1：用户手动选择的模型文件
路径 2：data_store 记录的最新模型文件（含同会话刚训练完的模型）
路径 3：扫描 output/models/ 目录，自动选择最新文件
```

**`model_predictor.py` — 新增 `reset()` 方法**

```python
def reset(self):
    self.model = None
    self.temp_model_path = None
    self.feature_detector.training_features = None
    self.feature_detector.normalization_method = None
```

**`main.py` — `handle_reset_progress()` 调用 `reset()`**

```python
self.prediction_manager.close_info_window()
self.prediction_manager.reset()  # 新增：清空预测器内部状态
```

---

#### 覆盖的场景

| 场景                   | 修复前          | 修复后              |
| -------------------- | ------------ | ---------------- |
| 跨会话加载模型文件预测          | ❌ 失败（无 CSV）  | ✅ 从 bundle 读取特征  |
| 自动化工作流（训练→预测，无选 CSV） | ❌ 失败         | ✅ 从 bundle 读取特征  |
| 切换模型后预测              | ❌ 可能用旧特征静默出错 | ✅ 每次加载完整覆写特征     |
| 重置后预测                | ❌ 可能沿用旧会话模型  | ✅ reset() 清空所有状态 |
| 加载旧格式 `.joblib`      | ✅ 静默使用错误特征   | ⚠ 明确报错，提示重新训练    |

## v1.11.9 (2026-03-21)

### 训练指标文件：`.npz` → `.json`，修复 schema 设计问题

#### 一、格式由 `.npz` 改为 `.json`

**原因**：`.npz` 是二进制格式，必须用 NumPy 才能查看，且对混合类型（数值 + 带类名 dict）支持笨拙。当前数据规模下 JSON 体积无压力，可读性更好。

**修复（`model_training.py`）**：

* 输出文件由 `metrics/{run_stem}.npz` 改为 `metrics/{run_stem}.json`
* 自定义 `_to_native()` 递归转换所有 numpy 类型（`np.float64`、`np.int32`、`np.ndarray`），`inf`/`nan` 替换为 `null`（避免 JSON 标准外的 `Infinity`）
* 自定义 `_write_metrics()` 渲染格式：顶层每个字段独占一行，数组值紧凑内联，兼顾可读性与文件体积

#### 二、修复 schema 设计问题

**问题一：confusion matrix 字段含义不明**

原 `[10, 0, 0, 9]` 不看代码无法判断 TP/TN/FP/FN 顺序，改为具名对象：
    {"tn": 10, "fp": 0, "fn": 0, "tp": 9}

**问题二：f_scores 第四个值恒为 0 的占位符**

### 修复各面板宽度不固定、长文字撑开相邻模块的问题

#### 问题现象

```python
if 'width' in kwargs or 'height' in kwargs:

```

各面板 `create_panel()` 传入实测尺寸（通过 `winfo_width()` / `winfo_height()` 在正常状态下采集）：

| 面板                 | width | height |

## v1.11.14 (2026-03-23)

### 预处理阶段支持通过菜单「重置」终止；复用训练的终止机制

#### 背景

v1.11.13 通过增密 `root.update()` 调用缓解了预处理阶段的 UI 卡顿，但仍存在一个更根本的问题：预处理运行期间，菜单栏的「🔄 重置」点击后没有任何响应，整个 UI 进入不可交互状态。训练阶段则可以随时通过菜单触发终止确认弹窗。

---

#### 根本原因分析

**原因一：`_handle_action_button` 的识别逻辑排除了预处理**

菜单「🔄 重置」绑定的是 `_handle_action_button`。该函数在 `_is_operation_running=True` 时，通过读取隐藏按钮 `action_btn` 的文字来判断是否允许终止：

```python
if self.action_btn.cget("text") == "终止训练":
    # 弹出确认框，设置 _operation_cancelled = True
```

`action_btn` 是一个从未被 `grid`/`pack` 到界面上的隐藏按钮，其 `text` 属性在此处被当作**状态标志**使用，而非真正的按钮文字。训练时 `_set_operation_running(allow_termination=True)` 将其设为 `"终止训练"`，条件命中；预处理时 `allow_termination=False` 将其设为 `"重置进度"`，条件不命中，函数直接返回，菜单点击静默无响应。

**原因二：`_confirm_and_process` 存在一个覆盖调用**

`_handle_preprocessing_start`（`main.py`）已经调用了 `_set_operation_running(allow_termination=True)`。但在用户确认分类窗口、处理真正开始前，`data_preprocessor.py` 的 `_confirm_and_process` 里还有一次额外调用：

```python
# data_preprocessor.py _confirm_and_process 第874行（修复前）
self.root.gui_manager._set_operation_running(True, "数据预处理", allow_termination=False)
```

这行代码是历史遗留，原意是在分类窗口确认后再次锁定按钮，但它把 `action_btn` 重置为了 `"重置进度"（disabled）`，覆盖了 `_handle_preprocessing_start` 的设置，导致即使修改了外层调用也无效。

**原因三：`_update_progress` 没有取消标志检查**

训练的终止链路是：`_operation_cancelled=True` → 下次 `progress_callback` 触发时检查标志 → 抛出 `InterruptedError`。`_update_progress` 中没有对应逻辑，即使 `_operation_cancelled` 被置为 `True`，预处理也不会停下来。

---

#### 修复方案

**`main.py` — `_handle_preprocessing_start`**

将 `allow_termination=False` 改为 `True`，使 `action_btn` 进入"终止训练"状态，`_handle_action_button` 的识别条件得以命中。同时新增 `InterruptedError` 捕获分支，更新 chip 状态：

```python
# 修复前
self._set_operation_running(True, "数据预处理", allow_termination=False)

# 修复后
self._set_operation_running(True, "数据预处理", allow_termination=True)
```

```python
except InterruptedError:
    log_message("预处理被终止", "WARNING")
    self.global_progress.update_chip('preprocess', '◼ 预处理: 已终止', 'orange')
```

**`data_preprocessor.py` — `_confirm_and_process`**

将覆盖调用同步修正，防止 `allow_termination=True` 的设置被回退：

```python
# 修复前
self.root.gui_manager._set_operation_running(True, "数据预处理", allow_termination=False)

# 修复后
self.root.gui_manager._set_operation_running(True, "数据预处理", allow_termination=True)
```

**`data_preprocessor.py` — `_update_progress`**

新增取消标志检查，对应训练 `progress_callback` 中的相同逻辑：

```python
def _update_progress(self, progress: float, message: str):
    if self.root and hasattr(self.root, 'gui_manager'):
        if self.root.gui_manager._operation_cancelled:
            raise InterruptedError("预处理被用户终止")
        self.root.gui_manager.update_global_progress(progress, message)
    if self.root:
        self.root.update()
```

**`data_preprocessor.py` — `_execute_processing`**

在 `except Exception` 前插入专用的 `InterruptedError` 捕获，防止其被当作普通错误处理并弹出错误框：

```python
except InterruptedError:
    log_message("预处理被用户终止", "WARNING")
except Exception as e:
    log_message(f"智能峰发现处理失败: {str(e)}", "ERROR")
    messagebox.showerror("处理错误", ...)
```

---

#### 附：`action_btn` 的设计说明

`action_btn` 是一个始终隐藏（未 `grid`/`pack`）的 `CTkButton`，其 `text` 属性在此程序中充当**操作状态的枚举值**：

| `text` 值                    | 含义                   |
| --------------------------- | -------------------- |
| `"重置进度"` + `state=normal`   | 空闲，菜单点击直接执行重置        |
| `"重置进度"` + `state=disabled` | 运行中，不可终止（原预处理/预测的状态） |
| `"终止训练"` + `state=normal`   | 运行中，可终止（训练和现在的预处理）   |
| `"终止训练"` + `state=disabled` | 用户已确认终止，等待重置完成       |

`_handle_action_button` 通过读取 `text` 而非独立布尔变量来区分状态，是历史形成的隐式约定。功能正确，但语义依赖按钮文字字面量，后续如需扩展建议改为专用 `_allow_termination` 布尔标志。

#### 三、修复重置时序：固定延迟 → 轮询等待

**原实现**：用户确认终止后，`root.after(1500, handle_reset_progress)` 固定等待 1500ms 再执行重置。

**问题**：

- 训练和预处理会因 `_operation_cancelled=True` 提前抛出 `InterruptedError` 退出，1500ms 通常够用，但属于经验值，不具可靠性
- 预测阶段不检查 `_operation_cancelled`，会继续跑完。如果预测耗时超过 1500ms，`handle_reset_progress` 会在预测仍在运行时执行，引发状态残留 bug

**修复**：将固定延迟改为轮询，每 100ms 检查一次 `_is_operation_running`，确认操作已自然退出后再执行重置：

```python
def _wait_and_reset():
    if self._is_operation_running:
        self.root.after(100, _wait_and_reset)
    else:
        self.handle_reset_progress()
self.root.after(100, _wait_and_reset)
```

各操作的退出路径：

| 操作  | 退出方式                                                                                  | 重置触发时机          |
| --- | ------------------------------------------------------------------------------------- | --------------- |
| 训练  | `_operation_cancelled=True` → `progress_callback` 抛 `InterruptedError` → `finally` 清理 | 下一折 `fit()` 完成后 |
| 预处理 | `_operation_cancelled=True` → `_update_progress` 抛 `InterruptedError` → `finally` 清理  | 下一次进度更新时        |
| 预测  | 不检查 `_operation_cancelled`，跑完后 `finally` 中 `_set_operation_running(False)`            | 预测自然完成后         |

## v1.11.16（2026-03-24）

### 新增：诊断报告导出时显示模型性能指标（`print_manager.py`、`model_predictor.py`）

#### 背景

此前"模型信息"段落仅输出模型类型与"训练状态: 已完成"，不包含任何量化指标，报告对生物医药背景读者的参考价值有限。

#### 实现

**`print_manager.py`——新增 `_load_metrics_summary(model_path)`**

根据模型路径（`models/*.joblib`）自动推导同名 metrics 文件路径（`metrics/*.json`），从中读取每折的混淆矩阵、AUC、F-score，用与 `visualization.py` 一致的 t 分布公式计算 95% CI，返回摘要 dict。

- 路径推导同时兼容正斜杠与反斜杠，兼容 `pathlib.WindowsPath` 对象（先 `str()` 转换再做字符串替换）
- 文件不存在或解析失败时静默返回 `None`，不影响报告其余内容

报告"模型信息"段落由原来 2 行扩充为：

```
模型信息:
  模型类型: PLSRegression
  交叉验证: 5折×20次重复 (100次迭代) (Youden's J)
  AUC-ROC:        0.984 ± 0.006  [95% CI: 0.978 ~ 0.990]
  灵敏度 [HCC]:    0.935 ± 0.018  [95% CI: 0.917 ~ 0.953]
  特异度 [Normal]: 0.970 ± 0.012  [95% CI: 0.958 ~ 0.982]
  F1 Score:       0.952 ± 0.010
```

类别标签直接取自 metrics JSON 的 `meta.class_names`，与训练时状态保持一致。

**`model_predictor.py`——`_apply_loaded` 同步 `model_path` 到 `data_store`**

原本只有 `model_training.py` 在训练完成后调用 `data_store.set_latest_trained_model`；通过文件选择器或目录扫描加载已有模型时，`model_path` 不写入 `data_store`，导致 `get_latest_model_info()` 返回 `has_model=False`，模型信息段完全不显示。

`_apply_loaded` 新增可选参数 `model_path: str = None`，有路径时自动同步到 `data_store`；`load_model` 的 case 1（用户手动选择）和 case 3（目录扫描）分别传入对应路径。

#### 同时修复

- **类别名称索引 bug**（`_generate_content`）：训练数据类别分布循环中，原代码用枚举变量 `i` 索引 `class_names`，改为用字典键 `int(cls)`，避免键顺序非 0/1 时名称错位。
- **删除永远不执行的分支**：数据集信息段"数据来源"行的三元表达式条件与外层 `if` 恒等（`total > 0` 蕴含 `class_0 > 0 or class_1 > 0`），`CSV文件导入` 分支永远不可达，直接删除该行。
