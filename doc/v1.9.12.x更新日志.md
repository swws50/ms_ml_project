## v1.9.12.7 (2026-03-07)

### 状态栏重构：ProgressComponent 集成 3 个状态 chip

#### 背景与动机

原来主界面 row=1 有一条由 `HelpSystem.create_progress_indicator()` 生成的**步骤向导条**（带编号圆圈 + 箭头 + 当前操作提示文字），row=3 有全局进度条 `ProgressComponent`（运行时显示、结束后隐藏）。二者都传递工作流状态信息，但向导条不提供"进行中 / 完成 / 失败"等结果反馈，且 `PreprocessingPanel` 内还有一个从不被更新的孤儿 `status_label`（row=2），整体引导不清晰。

#### 方案

将 `ProgressComponent` 改造为两层结构，并用它**替换**原步骤向导条：

```
row=1（chip 容器，始终可见）
  [ 预处理: 等待开始 ]   [ 训练: 未训练 ]   [ 预测: -- ]

row=3（进度条容器，仅运行时显示）
  步骤消息文字
  ████████████ 进度条
```

#### `ui_components.py` 变更

**`ProgressComponent` 新增 chip 行：**

- `__init__` 增加 4 个属性：`chip_frame`、`chip_preprocess`、`chip_train`、`chip_predict`
- `create(...)` 新增可选参数 `progress_parent=None`：
  - chip 行始终放在 `self.parent`（row=0）
  - 进度条 + 步骤消息若提供 `progress_parent` 则放入该容器（row=0/1），否则跟随 chip 行（row+1/2）
  - 这样 chip 容器和进度容器可以分别挂在主窗口的不同 row
- 新增 `update_chip(module, text, color)`：按 `'preprocess'` / `'train'` / `'predict'` 更新对应 chip 的文字和颜色
- 新增 `reset_chips()`：将三个 chip 重置为初始灰色文字
- `hide()` / `show()` 只操作进度条和步骤消息，**chip 行不受影响**

**`PreprocessingPanel` 清理：**

- 删除 `_create_panel_content` 中的孤儿 `status_label`（row=2）及相关 `grid_rowconfigure`
- 删除 `update_status()` 方法（从未被有效调用）

#### `help_system.py` 变更

- 删除 `__init__` 中的 `progress_frame`、`progress_labels`、`progress_indicator` 三个 UI 属性
- 删除 `create_progress_indicator()` 方法（整体约 50 行，向导条 UI 全部移除）
- `update_progress_display()` 简化为 `pass`（原依赖已删的 `progress_labels`）
- 删除 `complete_step()` 方法（项目中从未被调用）

#### `main.py` 变更

- `_create_global_progress()`：创建两个独立容器
  - `chip_container` → `root` row=1（`ProgressComponent` 的 `self.parent`）
  - `progress_container` → `root` row=3（通过 `progress_parent=` 传入）
- 移除 `self.help_system.create_progress_indicator(...)` 调用
- 移除两处 `advance_step()` 调用（`"select_model"`、`"train_model"`），原仅打日志，向导条删除后无实际意义
- 重置逻辑：移除步骤循环重置 + `update_progress_display()`，只保留 `hide_all_tips()`

**各操作节点的 chip 更新逻辑：**

| 操作       | 开始             | 成功         | 终止 / 取消   | 异常                |
| -------- | -------------- | ---------- | --------- | ----------------- |
| 预处理      | `进行中...`（蓝）    | `完成`（绿）    | `等待开始`（灰） | `失败`（红）+ re-raise |
| 训练       | `进行中...`（蓝）    | `完成`（绿）    | `已终止`（橙）  | `失败`（红）+ re-raise |
| 预测模型文件选择 | —              | `模型已加载`（绿） | —         | —                 |
| 预测执行     | 不更新（保持"模型已加载"） | 不更新        | 不更新       | 不更新               |

> 预测 chip 仅在用户选择模型文件时更新（`PredictionPanel._on_model_file_select` 回调），不对预测结果做监测，避免因结果检测引入噪声。

### 已知遗留 Bug：预测报"无法检测训练特征"

#### 现象

在某些工作流下执行预测，结果面板显示：**"预测失败: 无法检测训练特征"**

#### 错误来源

```
model_predictor.py → predict_file()
  → feature_detector.load_training_features()   # 返回 None
  → {"success": False, "error": "无法检测训练特征"}
```

`data_processing.py` `FeatureDetector.load_training_features()` 的逻辑：

```python
data_file = data_store.get_training_data_path()     # ① 会话内选过 CSV？
if not data_file or not os.path.exists(data_file):
    data_file = OUTPUT_FILES['processed_data']       # ② 回退到 data.csv
    if not os.path.exists(data_file):
        return None, None                            # ← 触发错误
```

#### 根本原因

**模型保存时只保存了 sklearn 模型对象本身，没有保存训练特征的 m/z 列表。**

`model_training.py` 中：

```python
dump(self.best_model, model_path)   # 只保存模型，无特征元数据
```

预测时，`load_training_features` 需要读取训练 CSV 才能得到 m/z 特征列表，用于从预测样本中提取对应峰位的强度（特征对齐）。如果：

- 当前会话没有通过"选择 CSV 文件"按钮加载训练数据（`data_store._training_data_path` 为 `None`）
- 且输出目录下的 `data.csv` 不存在或路径不匹配

则 `load_training_features` 返回 `None`，导致预测失败。

`data_store.set_training_data_path()` 只在两处被赋值：

1. `data_processing.open_data_file()`（用户点击"选择 CSV 文件"）
2. `automated_workflow.py`

`DataPreprocessor`（预处理完成后）**不调用** `set_training_data_path`，因此仅做预处理不会填充该路径。

此 bug 与本次 UI 改动无关，属早期设计遗留问题，之前因用户总在同一会话内按顺序完成"预处理→选CSV→训练→预测"而未触发。

#### 正确的修复思路（待实现）

在 `save_training_results()` 保存模型时，将训练特征列表和归一化方法一并打包存入同一 `.joblib` 文件：

```python
# model_training.py save_training_results() 中
model_bundle = {
    "model": self.best_model,
    "training_features": <从 data_store 或 DataFrame 中取得的 m/z 列表>,
    "normalization_method": <从文件名或 config 取得>
}
dump(model_bundle, model_path)
```

在 `model_predictor.py load_model()` 中检测是否为 bundle 格式：

```python
loaded = load(model_path)
if isinstance(loaded, dict) and "model" in loaded:
    self.model = loaded["model"]
    self.feature_detector.training_features = loaded.get("training_features")
    self.feature_detector.normalization_method = loaded.get("normalization_method")
else:
    self.model = loaded   # 兼容旧格式
```

这样预测时完全不依赖训练 CSV 是否存在，也消除了 `load_training_features` 读文件失败的可能。**注意：旧格式 `.joblib` 需保持向后兼容。**

## v1.9.12.7.1 (2026-03-07)

### 修复状态栏 chip 时机错误

#### 问题1：按下预处理按钮后 chip 显示"等待开始"而非"进行中"

**根因**：`data_preprocessor.show_classification_dialog()` 调用 `_create_classification_window()` 后立即返回（无 `wait_window`），导致 `_handle_preprocessing_start` 在分类窗口打开的瞬间就执行完后续逻辑，将 chip 从"进行中"覆写回"等待开始"。

**修复**（`data_preprocessor.py`）：在 `show_classification_dialog` 末尾加 `wait_window`，使调用方阻塞至窗口关闭。`wait_window` 内部运行嵌套 Tcl 事件循环，UI 不卡死，进度窗口等交互正常。

#### 问题2：预处理完成后 chip 仍显示"等待开始"而非"完成"

**根因**：`main.py` 用 `data_store.has_training_data()` 判断预处理是否成功，但 `data_preprocessor.py` 从未调用 `data_store.set_training_data()`，该函数只在手动"选择 CSV"或自动化工作流时被赋值，因此永远返回 False。

**修复**（`data_preprocessor.py` + `main.py`）：

- `DataPreprocessor` 新增 `self.preprocessing_completed = False` 标志
- `_save_and_notify_results` 保存成功时置 `True`
- `show_classification_dialog` 每次调用时重置为 `False`
- `main.py._handle_preprocessing_start` 改为检查 `self.data_preprocessor.preprocessing_completed`

## v1.9.12.7.2 (2026-03-07)

### 修复自动化工作流与状态栏的冲突

#### 背景

v1.9.12.8 在 `show_classification_dialog` 末尾加入 `wait_window` 后，`automated_workflow.py` 的轮询监控 `_monitor_preprocessing_completion` 出现计时错误：`start_time` 在对话框关闭后才被记录，导致 CSV 文件的修改时间永远早于 `start_time`，条件 `os.path.getmtime(csv_path) > start_time` 始终为 False，训练步骤永远无法触发。

此外，自动化流程绕过了 `_handle_preprocessing_start`，chip 在整个自动化过程中始终停在默认灰色。

#### 方案：回调机制替代轮询

在 `DataPreprocessor` 引入 `on_complete_callback`，预处理成功保存结果时主动触发，外部按需注册。手动流程和自动化流程统一走回调，不再依赖 `wait_window` 结束后的状态检查。

自动化流程执行期间，三个 chip 统一显示 `⚙ 自动化中...`，流程结束后恢复各自最终状态。

#### `data_preprocessor.py` 变更

- `__init__` 新增 `self.on_complete_callback = None`
- `_save_and_notify_results` 保存成功后触发：`self.root.after(0, self.on_complete_callback)`（`root.after(0, ...)` 在 `wait_window` 的嵌套事件循环中安全调度，UI 不冻结）

#### `main.py` 变更

- `_handle_preprocessing_start`：调用 `show_classification_dialog` 前注册 lambda 回调（成功时更新 chip 为绿色 ✓），窗口关闭后在 `finally` 里清理回调；移除 `wait_window` 结束后的 `preprocessing_completed` 标志检查，改为仅在未完成时重置灰色

#### `automated_workflow.py` 变更

- 删除 `_monitor_preprocessing_completion`（轮询逻辑完全移除）
- `_preprocessing_step`：设三个 chip 为 `⚙ 自动化中...`，注册 `_on_preprocess_done` 回调，窗口关闭后清理回调
- 新增 `_on_preprocess_done`：回调触发后 `root.after(1000, _training_step)`
- `_training_step`：移除废弃的 `_detected_csv_path` 引用，直接调用 `_find_latest_data_csv()`
- `_prediction_preparation_step` 成功结尾：恢复三个 chip 最终状态（预处理/训练绿色 ✓，预测绿色 ✓）；失败分支：预处理绿、训练红 ✗、预测灰 ○
