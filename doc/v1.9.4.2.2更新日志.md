Bug描述
-----

### 问题现象

当用户从"未归一化"模式切换到"归一化"模式后，直接进行预测操作时，系统**跳过了归一化因子的必要检查**，导致应该报错的情况没有报错。

### 复现步骤

1. 启动系统，默认为"归一化"模式
2. 切换到"未归一化"模式
3. 进行一次预测操作（成功）
4. 切换回"归一化"模式
5. 直接进行预测操作
6. **预期行为**: 如果没有归一化因子应该报错
7. **实际行为**: 系统使用了缓存的 `None` 值，跳过了检查

* * *

根本原因分析
------

### 问题根源

在 `feature_detector.py` 的 `load_training_features()` 方法中存在缓存逻辑问题：
    def load_training_features(self, force_reload=False):
        # 如果已经检测过且不需要强制重新加载
        if not force_reload and self.training_features is not None:
            return self.training_features, self.normalization_factor  # ← 问题所在

### 问题机制

1. **第一次预测（未归一化模式）**:
   
   * 调用 `load_training_features()`
   * 执行 `_detect_normalization_factor()` → 返回 `None`（因为是未归一化模式）
   * 缓存: `self.normalization_factor = None`

2. **用户切换到归一化模式**:
   
   * 只更新了 `data_store` 的状态
   * `FeatureDetector` 实例的缓存**没有失效**

3. **第二次预测（归一化模式）**:
   
   * 调用 `load_training_features()`
   * 发现 `self.training_features is not None` → **直接返回缓存**
   * 返回旧的 `normalization_factor = None`
   * **跳过了 `_detect_normalization_factor()` 的检查和报错逻辑**

### 为什么会发生

缓存逻辑只检查了 `training_features` 是否存在，但**没有考虑归一化状态的改变**。这导致归一化模式切换后，缓存的归一化因子与当前模式不匹配。

* * *

解决方案
----

### 修复策略

在 `load_training_features()` 方法中添加**归一化状态变化检测**，当检测到模式切换时强制重新加载。

### 修复代码

**修改文件**: `feature_detector.py`

**修改方法**: `load_training_features()`
    def load_training_features(self, force_reload=False):
        """
        检测训练特征和归一化因子

        参数:
            force_reload: 是否强制重新检测

        返回:
            tuple: (特征列表, 归一化因子) 或 (None, None)
        """
        # 检查归一化状态是否改变，如果改变则强制重新加载
        current_norm_enabled = data_store.is_normalization_enabled()
        cached_norm_factor = self.normalization_factor

        # 判断是否需要重新加载
        need_reload = (
            force_reload or 
            self.training_features is None or
            (current_norm_enabled and cached_norm_factor is None) or  # 切换到归一化但没有因子
            (not current_norm_enabled and cached_norm_factor is not None)  # 切换到非归一化但有因子
        )

        if not need_reload:
            return self.training_features, self.normalization_factor

        # 后续代码保持不变...

### 修复逻辑说明

新增的重新加载触发条件：

| 条件                                                            | 说明                      | 作用       |
| ------------------------------------------------------------- | ----------------------- | -------- |
| `force_reload`                                                | 强制重新加载标志                | 原有逻辑     |
| `self.training_features is None`                              | 没有缓存的特征                 | 原有逻辑     |
| `current_norm_enabled and cached_norm_factor is None`         | **切换到归一化模式但缓存中没有归一化因子** | **修复核心** |
| `not current_norm_enabled and cached_norm_factor is not None` | 切换到非归一化模式但缓存中有归一化因子     | 保持一致性    |

经验总结
----

### 缓存陷阱

当使用缓存机制时，必须考虑：

1. **缓存失效条件**: 什么情况下缓存应该失效？
2. **状态依赖**: 缓存的数据是否依赖于外部状态？
3. **状态变化检测**: 如何检测外部状态的变化？

### 教训

* 缓存不仅要检查"是否有数据"，还要检查"数据是否仍然有效"
* 跨模块的状态（如 `data_store` 中的设置）改变时，依赖该状态的缓存应该失效
* 单元测试应该覆盖状态切换场景
